# 🎬 背景设定

发版节奏：双周迭代（每两周发一次版）。

时间设定：本周是发布周，周四是发版日。本周五到下周五是下一个开发周。

当前版本：线上是 v1.0.0，master 和 next 分支代码完全一致。

角色：开发者小明（负责紧急修 Bug）、开发者小红（负责开发新功能）、Owner（仓库管理员，负责合并代码和发版）。

# 💥 场景 A：如果不引入 next 分支（Gitlab Flow 1.0 的痛点）

到了周三，距离周四发版只剩一天了。

小红 写完了“双十一促销”的新功能（这是一个下个月才上的功能，绝对不能在周四发版）。她把 MR 提交到了 master。

小明 发现线上有一个支付 Bug，必须赶在周四前修复。他也把 MR 提交到了 master。

Owner 把两人的代码都合并进了 master，并且执行了 npm version patch 打上了 v1.0.1 的 tag。

致命问题出现了：Owner 要把 master 合并到 test 分支进行预发测试。此时 test 里面不仅有小明的 Bug 修复，还混入了小红的“双十一促销”代码。

结果：由于小红的功能没测试完，带有小红的代码就不能发版，导致小明的紧急 Bug 修复也被卡住发不出去。如果强行把代码回退，又会极其麻烦。

# ✨ 场景 B：引入 next 分支后（Gitlab Flow 2.0 的完美运作）

为了解决上面的问题，引入了 next 分支（从 master 复制出来，作为“冷冻舱”）。

第一阶段：发布周（周三）
小红的操作（新功能）：小红知道这周是发布周，新功能不能上。于是她把 MR 提交到了 next 分支。

Owner 合并代码到 next。注意：next 分支不打 tag。

小明的操作（紧急修复）：小明修的是线上 Bug，必须本周发。于是他把 MR 提交到了 master 分支。

Owner 合并代码到 master，并严格执行：npm version patch，打上 v1.0.1 的 tag，推送。

Owner 的发版：Owner 将 master 合并到 test，然后合并到 production。

奇迹发生了：此时 test 和 production 里只有小明的 Bug 修复（v1.0.1），完全没有小红的促销代码。发版非常干净、安全。

第二阶段：发版结束，进入下一个开发周（下周一）
发版顺利完成。新的开发周开始了，这时候需要把之前积压的新功能释放出来。

Owner 的合并：Owner 发起一个 MR，把 next 分支合并回 master 分支。

此时，master 里面才正式有了小红的“双十一促销”代码。

Owner 再次执行 npm version minor（因为加了新功能），打上 v1.1.0 的 tag。

此时 master 和 next 再次保持同步，准备迎接新一轮的开发。

# 📝 总结：为什么要这么干？

这个流程的核心目的就是隔离风险。

master 是随时可以发版的稳定代码库（只接 Bug 修复和按时的功能发布）。

next 是蓄水池，用来存放那些开发完了、但没到发版时间（不能见光）的代码。

Tag 永远只打在 master 上，保证了版本历史的绝对干净，next 只是临时借用的工作区。
